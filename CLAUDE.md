# Glimmerstones — дизайн-документ

Мобильная браузерная игра-сортировка камней. Подарок; приветствие для **Зилант**.
Название: **Glimmerstones** (подзаголовок в интерфейсе: «мерцающие камни»).
Язык интерфейса — русский. Всё своё: графика и звуки генерируются кодом, никаких чужих ассетов.

## Ощущение
Спокойно, красиво, затягивающе. Нет таймеров, жизней, проигрышей, рекламы, покупок,
регистрации, сети. Любой ход можно отменить. Главное — сочные камни и момент сбора тройки.

## Механика
- Уровень: 5–12 полочек. У полочки **передний ряд из 3 ячеек** + стопка скрытых слоёв
  (каждый слой — до 3 камней). Скрытые слои рисуются затемнёнными (видно цвет/форму).
- Двигать можно только камни переднего ряда. Ход = камень из переднего ряда полки A
  в свободную ячейку переднего ряда полки B (B ≠ A).
- Ввод: тап по камню → он выделен (приподнят, светится) → тап по полке со свободной
  ячейкой → перелёт. Тап по другому камню меняет выбор, тап мимо снимает. Перетаскивание
  пальцем тоже работает.
- **Тройка**: 3 одинаковых камня в переднем ряду (т.е. ряд заполнен одним цветом) — сливаются
  и исчезают (с этапа 3 — улетают в картинку).
- **Выезд слоя**: когда передний ряд полностью пуст, следующий слой выезжает вперёд.
- **Победа**: собраны все камни.
- **Тупик**: в передних рядах нет ни одной свободной ячейки (а тройки собираются
  автоматически, значит собрать нечего). Мягкое окошко без слова «проигрыш»:
  «Отменить ход», «Добавить полочку», «Начать заново».
- Отмена без ограничений. «Добавить полочку» — один раз за уровень, добавляет пустую полку.
- **Подсказка** (без ограничений): солвер в Web Worker (`src/hint`) от текущей позиции
  поднимает нужный камень и подсвечивает целевую полку; дальше достаточно тапнуть полку.
  Если позиция уже не решается — солвер ищет в истории ближайшую решаемую позицию и мягко
  предлагает «Вернуться на N ходов»; после отмены подсказка показывается сама.
  Если солвер упёрся в лимит узлов — показывает его лучший эвристический ход.
- Цвет камня всегда связан с формой огранки: круг, квадрат, сердце, капля, звезда,
  шестиугольник, овал, треугольник. Значит, **не больше 8 цветов** в уровне.

### Принятые упрощения (решения без вопросов)
- Позиция камня внутри ряда на логику не влияет (ряд из 3 — тройка = весь ряд одного цвета).
  Позиции хранятся только для стабильной отрисовки. И при тапе по полке, и при броске
  перетаскиванием камень ложится в ближайшую к точке свободную ячейку.
- Перетаскивание: камень «висит» чуть выше пальца, бросок засчитывается по полке под камнем
  (или ближайшей в пределах 0.6 ячейки); мимо — камень плавно возвращается на место.
- Анимации не блокируют ввод: новый ход мгновенно доигрывает (flush) текущие анимации.
- Отмена/«Заново» показывают результат сразу, без обратной анимации.
- Окна победы/тупика появляются после окончания анимаций.
- Тап по камню всегда выбирает его (даже на целевой полке); чтобы положить камень,
  тапают по свободной ячейке или по самой полке.
- Видно затемнённым только следующий скрытый слой; число остальных — бейдж «+N».
- Слой выезжает только когда передний ряд пуст целиком. Камни слоя занимают ячейки слева.
- Скрытые слои могут быть неполными (1–3 камня); пустые ячейки на старте — только в передних рядах.
- Отмена — через снимки состояния. Добавленная полочка постоянна: она дописывается и
  в текущее состояние, и во все снимки истории, поэтому отмена её не убирает.
  «Начать заново» возвращает уровень к исходному виду и снова разрешает добавить полочку.
- Тупик определяется только по отсутствию свободных ячеек («мягкие» тупики, когда ходы
  есть, но решения уже нет, не детектируются — всегда можно отменить).

## Генератор уровней
- **Уровни генерируются при сборке**: `npm run levels` (входит в `npm run build`) прогоняет
  генератор и солвер и пишет `src/data/levels.json` (240 уровней, ~25 с). На телефоне солвер
  при старте уровня не запускается; для подсказки — только в Web Worker.
  Тест `levelpack.test.ts` проверяет, что JSON совпадает с генератором.
- Параметры: `colors` (3–8), `triplesPerColor`, `shelves` (5–12), `depth` (макс. число
  скрытых слоёв), `emptyCells` (свободные ячейки на старте).
- Детерминирован по seed: PRNG mulberry32, seed = hash(номер уровня, номер попытки).
  Уровень N всегда одинаковый.
- Каждый уровень проверяется солвером; не решился — следующая попытка.
  Каждые 10 неудач — +1 пустая ячейка.
- **Метрика сложности** (`difficulty.ts`): доля побед «казуального» игрока (собирает тройку,
  если может, любит класть к своему цвету, иначе случайно) на 80 прогонах.
  Из 6 решаемых кандидатов берётся ближайший к целевой доле `targetWinRate(n)`
  (≈0.9 в начале → 0.5–0.6 позже, передышки ≈0.85).
- Кривая: 1–3 уровни — 3–4 цвета, без скрытых слоёв; дальше постепенно больше цветов,
  троек и слоёв; каждый 5-й уровень — передышка (параметры на ступень проще).
  Таблица — в `src/core/levels.ts`.

## Солвер
Итеративный DFS (решения бывают в сотни ходов) с мемоизацией посещённых состояний и лимитом узлов. Каноничный ключ состояния:
каждая полка → (мультимножество переднего ряда, скрытые слои), полки отсортированы
(порядок полок не важен). Отсечения: ходы в пустые полки эквивалентны — пробуем одну;
приоритет ходов, достраивающих тройку или кладущих к камню того же цвета.

## Картинка-награда (этап 3)
- Формат JSON (`src/pictures/*.json`, загружаются автоматически):
  `{ "id", "name", "width", "height", "palette": { "a": "#rrggbb", ... }, "rows": ["..aa..", ...] }`.
  `.` — пустая клетка; ключ палитры — один символ (не цифра, не `.`); размер 8..32;
  до 8 цветов; порядок ключей палитры = индекс цвета уровня = огранка камня.
  Проверка — `validatePicture` (при генерации уровней и в тестах).
- 13 своих картинок (сердце, звезда, яблоко, клубника, гриб, рыбка, цветок, кекс, кот, домик,
  бабочка, радуга, букет), нарисованы простыми фигурами без сглаживания.
  **Добавить картинку**: положить JSON в `src/pictures/`, выполнить `npm run levels`.
  Будущий конвертер «фото → картинка» должен просто выдавать этот же JSON.
- Привязка к уровням — при генерации (`assignPictures`): палитра размером
  [нужно цветов − 2 .. нужно цветов] по кривой, давно не встречавшаяся — первой.
  Цвета уровня = палитра; общее число троек берётся из кривой и делится между цветами
  пропорционально площади (`distributeTriples`), но не меньше числа связных областей цвета
  и не больше 8 на цвет.
- Нарезка (`partition`): каждый цвет режется на столько связных (8-связность) кусочков,
  сколько у него троек: семена — самая нижняя клетка + farthest-point, затем сбалансированный
  рост регионов. Кусочки цвета заполняются снизу вверх, камешки в кусочке — тоже снизу.
- Состояние картинки выводится из доски (собрано троек цвета = всего − осталось камней / 3),
  поэтому отмена/«Заново» просто синхронизируют картинку (`PictureView.sync`).
- Камни уровня окрашены в цвета палитры, но светлота зажата в 0.40..0.72, чтобы чёрные/белые
  цвета картинки были видны на бархате (`gemStylesForPalette`); картинка — в точных цветах.
- Полёт: тройка приподнимается и светится (220 мс), камни по очереди летят по дуге
  в центр своего кусочка и уменьшаются; кусочек «засыпается» падающими камешками.
- Поле делится: картинка сверху (120..230 px, что осталось после полок), полки снизу.
- Финал: полки уходят под вуаль, картинка вырастает к центру, по ней бежит волна блеска,
  искры; затем карточка «Картинка «…» готова и сохранена в галерею», «Дальше».
  Название картинки до конца не показывается — сюрприз.
- Галерея (этап 3 — только сохранение): `storage.ts`, ключ `glimmerstones.v1`,
  `gallery[id] = { count, firstLevel, lastLevel }`.
- Производительность: DPR canvas ограничен 2; улёгшиеся камешки кэшируются в offscreen-canvas,
  вживую рисуются только падающие. Проверка: 4× замедление CPU в Chromium — ~56 fps.

## Экраны и прогресс (этап 4)
- Три экрана (DOM-секции, `main.ts` переключает): **старт** (логотип, «Привет, Зилант!»,
  фраза дня, «Играть · Уровень N / Продолжить уровень N», «Галерея · Собрано a из b»,
  плавающие камни на фоне), **игра** (шапка: домой · уровень · звук), **галерея**
  (сетка 3 колонки: собранные — мозаикой, остальные — «?»; тап → большая картинка,
  сколько раз собрана и на каком уровне впервые). Имя — `PLAYER_NAME` в `strings.ts`.
- Прогресс (`storage.ts`, `glimmerstones.v1`): `level` (следующий), `current`
  (незаконченный уровень: доска + вся история отмены + использована ли полочка — сохраняется
  после каждого хода и при сворачивании), `gallery`, `settings {sound, vibration}`.
  `Game.restore` проверяет, что снимок подходит уровню (иначе уровень начинается заново).
- Победа: прогресс сохраняется сразу при начале финала; карточка «Дальше» / «В галерею».
  «Дальше» — мягкий переход (поле уходит вниз и прозрачнеет, новое приходит сверху).
- После 240 уровней игра бесконечна: уровни 61..240 идут по кругу (номер растёт).
- Отладочные стрелки уровней и `#N` в адресе убраны; в dev есть `window.__gs` для автотестов.

## Отрисовка (этап 2)
- Стиль «шкатулка»: бархатные лотки, золотой бортик спереди (рисуется поверх низа камней),
  фон — CSS-градиент, canvas прозрачный.
- Камни: огранка из контура формы (коронные грани с освещением сверху-слева, площадка,
  звёздные грани, блик, отражённый свет), пре-рендер в `GemAtlas` (обычный/затемнённый/ореол)
  под текущий радиус и DPR. Мерцание — редкие искорки-спрайты со своим ритмом у каждого камня.
- Статические слои (лотки, бортики) кэшируются в offscreen-канвасах; во время перестройки
  раскладки (добавили полку) рисуются напрямую с интерполяцией позиций.
- `BoardView` отстаёт от логики: у каждой полки очередь шагов по времени
  (приземление → тройка → выезд слоя), перелёт по дуге — отдельный слой поверх.
  Шаги строятся из событий хода через `setCell` + `applyEvent` (ядро).
- Раскладка: 2 колонки; 1 колонка, если камни так крупнее на 15%+.

## Стек
- Vite + TypeScript (strict), Canvas 2D, Vitest. Без игровых движков и рантайм-зависимостей.
- Портрет, mobile-first. devicePixelRatio, safe-area (env(safe-area-inset-*)),
  запрет зума/прокрутки (`touch-action: none`, viewport meta, preventDefault).
- Камни рисуются кодом (градиенты, грани, блик, мерцание), пре-рендер в offscreen-канвасы.
- Звук — Web Audio синтез (клик, звон тройки, мелодия победы), кнопка mute; вибрация через
  `navigator.vibrate` где есть.
- Прогресс (уровень, галерея, настройки) — localStorage.
- Этап 6: PWA (manifest, иконка, service worker), GitHub Pages.

## Структура
```
src/
  core/        чистая логика без DOM: types, rng, board, game, solver, generator,
               difficulty, levels (кривая + выбор картинок), levelpack, hint,
               picture (формат, распределение троек, нарезка) (+ *.test.ts)
  data/        levels.json — сгенерированные уровни
  levelData.ts загрузка уровней
  render/      canvas: layout, gems (огранка + атлас), shelves, view (анимации), particles,
               picture (картинка-награда)
  anim/        easing
  hint/        Web Worker с солвером для подсказки + клиент
  input/       тапы и drag (pointer events)
  audio/       синтез звуков
  ui/          gameScreen, startScreen, galleryScreen, dom (карточка, тост), icons,
               strings.ts (все русские строки)
  pictures/    JSON-картинки + index.ts (загрузка через import.meta.glob)
  storage.ts   localStorage
  main.ts
scripts/
  generate-levels.ts   генерация уровней при сборке
```

## Правила кода
- `src/core` не импортирует ничего из DOM/рендера; всё покрыто тестами Vitest.
- Состояние иммутабельно по смыслу: ход возвращает новое состояние (удобно для отмены и солвера).
- Все строки интерфейса — в `src/ui/strings.ts`.
- Перед коммитом: `npm run build` и `npm test` зелёные.
- Код и идентификаторы — на английском, комментарии кратко.

## Команды
- `npm run dev -- --host` — dev-сервер для телефона в той же сети
- `npm test` — тесты, `npm run build` — генерация уровней + typecheck + сборка
- `npm run levels` — только перегенерировать уровни
- Скрипты на TS запускаются нативно Node 22 (type stripping) — импорты с расширением `.ts`,
  только «стираемый» синтаксис (без enum/namespace).

## Git
- Автор и коммиттер — владелец репозитория (задано в `git config` репозитория).
- В сообщениях коммитов нет строк Claude-Session и Co-Authored-By;
  `.claude/settings.json` отключает атрибуцию, CI роняет сборку, если они есть в истории.

## Деплой
GitHub Pages через Actions (`.github/workflows/deploy.yml`) на каждый push в `main`:
тесты → сборка с `BASE_PATH=/<имя-репо>/` → публикация. Vite `base` берётся из `BASE_PATH`;
manifest и service worker (этап 6) — с относительными путями от base.
Проверка на телефоне — по ссылке Pages после каждого этапа.
